## Context

See [proposal.md](proposal.md) for motivation and the delta specifications for
the required [validation-engine](specs/validation-engine/spec.md) and
[rule-extension](specs/rule-extension/spec.md) behavior.

Today `internal/parser/pgquery.go` imports `pg_query_go/v6`, calls its CGO
entry point, and immediately copies the returned PostgreSQL protobuf tree into
immutable parser-owned `Node`, `Field`, and `Value` values. The engine and
public rule API already depend only on that parser-neutral tree. This is the
right boundary for adding a second backend: generated parser types remain
internal, while traversal, prepared values, rules, errors, and observability do
not need backend branches.

The repository currently pins `pg_query_go/v6` v6.2.2 and documents PostgreSQL
17 grammar compatibility. The no-CGO backend must therefore reproduce that
grammar and protobuf shape closely enough that every field exposed through the
public `Statement` facade retains its meaning. Merely recognizing `UPDATE`,
`DELETE`, and `WHERE` is insufficient because custom rules may inspect any
parser-neutral field.

The candidate assessment below is a snapshot taken on 2026-09-13. Exact
project-level latency, allocation, startup-memory, and binary-size numbers do
not exist yet and must be generated by the implementation tasks; upstream
measurements are treated as directional evidence only.

## Goals / Non-Goals

**Goals:**

- Keep the CGO-enabled path on the existing official `pg_query_go/v6`
  integration.
- Make an ordinary `CGO_ENABLED=0` build select a no-CGO backend without a
  custom build tag or public configuration.
- Reuse one conversion and traversal implementation for both backends.
- Make grammar, AST, rule-result, error, concurrency, and observability parity
  release gates backed by a shared corpus.
- Publish reproducible cold/warm performance and binary-footprint comparisons.
- Keep parsing synchronous on the caller goroutine and preserve the current
  context-precedence behavior.
- Allow no-CGO support and audit mode to ship independently while preserving
  the safety contract of each capability.

**Non-Goals:**

- Supporting TinyGo; the selected WASM backend depends on WebAssembly threads,
  which its maintainers state TinyGo does not support.
- Allowing callers to choose, register, or detect a parser backend at runtime.
- Maintaining two independently designed semantic AST mappings.
- Treating benchmark parity as a requirement. Behavioral parity is mandatory;
  the expected no-CGO performance and footprint costs are documented tradeoffs.
- Expanding beyond the parser operations SQLGuard uses (`Parse` and conversion
  of its result).
- Implementing or changing audit-mode runtime behavior.

## Decisions

### 1. Use `wasilibs/go-pgquery` as the no-CGO backend

The no-CGO build will call `github.com/wasilibs/go-pgquery`. It compiles
`libpg_query` to WebAssembly and runs it with wazero, requires no CGO by
default, and returns `pg_query_go/v6` protobuf types. Its current `main`
dependency set uses `pg_query_go/v6` v6.2.2—the same version currently pinned
by this repository—and wazero v1.12.0. The upstream project runs the
`pg_query_go` and `libpg_query` test suites and reports no known behavior
differences, while explicitly acknowledging that WASM-specific defects remain
possible. See the upstream [compatibility and performance notes](https://github.com/wasilibs/go-pgquery#readme),
[adapter implementation](https://github.com/wasilibs/go-pgquery/blob/main/pg_query.go),
and [dependency manifest](https://github.com/wasilibs/go-pgquery/blob/main/go.mod).

This is the only evaluated option that combines no-CGO operation with the same
PostgreSQL-derived grammar and protobuf schema as the current backend. It
therefore minimizes the amount of new safety-sensitive code: only the raw parse
entry point varies, while conversion and all downstream semantics remain
shared.

The implementation will pin an immutable reviewed `go-pgquery` revision rather
than tracking `main`. Its `pg_query_go/v6` version must match the direct
dependency used by SQLGuard. Dependency updates are accepted only after the
full cross-backend conformance suite passes.

#### Candidate comparison

| Candidate | Grammar and AST | Performance and size | Operational and maintenance constraints | Decision |
| --- | --- | --- | --- | --- |
| `pg_query_go/v6` | Actual PostgreSQL server parser and PostgreSQL protobuf tree; current PostgreSQL 17 baseline | Existing fast baseline; upstream notes that C-side allocations are not fully visible to Go benchmarks | Requires CGO and a C compiler; cross-compilation and toolchain upgrades are more involved; BSD-3-Clause plus PostgreSQL notices | Retain for `cgo` builds |
| `wasilibs/go-pgquery` | `libpg_query` compiled to WASM; returns the same `pg_query_go/v6` protobuf types and imports upstream test suites | Upstream measurements show roughly 4–5x slower parsing than CGO; embedded WASM and wazero are expected to increase binary size and cold-start memory, with exact SQLGuard numbers still to measure | No C toolchain at consumer build time; no TinyGo; package currently has no tagged releases, so pin a reviewed pseudo-version; MIT with inherited notices and wazero dependencies | **Selected for `!cgo`** |
| `bytebase/omni/pg` | Independent pure-Go recursive-descent PostgreSQL parser with its own 210+ node AST and PostgreSQL regression corpus | No trustworthy apples-to-apples SQLGuard measurement yet; avoids a WASM runtime | Young API and separate AST require a large, continuously maintained semantic mapper; exact PostgreSQL 17 parse-tree parity is not inherent; MIT | Reject for this change; reconsider only if it gains a stable compatibility contract |
| `auxten/postgresql-parser` | Pure-Go parser derived from CockroachDB v20.1.11, described as “CockroachDB style PostgreSQL,” with a different AST | No maintained comparable benchmark or footprint evidence | Its README still lists parser-test and built-in-function gaps; grammar lineage and AST differ materially from the PostgreSQL 17 baseline; Apache-2.0 | Reject |
| Locally maintained `libpg_query.wasm` wrapper | Could preserve the same grammar and protobuf wire format | Similar WASM runtime cost to `go-pgquery` | SQLGuard would own the C-to-WASI toolchain, patches, artifact generation, runtime ABI, and security updates | Reject while the packaged adapter remains viable |

Primary sources for the rejected parsers are the official
[`bytebase/omni` repository](https://github.com/bytebase/omni) and
[`auxten/postgresql-parser` repository](https://github.com/auxten/postgresql-parser).
The current CGO baseline is documented by
[`pg_query_go`](https://github.com/pganalyze/pg_query_go), which uses actual
PostgreSQL server source and publishes its benchmark caveats. All dependency
licenses and notices must be reviewed and included as required before release;
the preliminary set is BSD-3-Clause/PostgreSQL for `pg_query_go`, MIT and
inherited notices for `go-pgquery`, and Apache-2.0 for wazero.

### 2. Select the backend with standard Go build constraints

Exactly one small backend file will provide `parseBackend`:

- `backend_cgo.go` with `//go:build cgo` imports and calls
  `pg_query_go/v6.Parse`.
- `backend_nocgo.go` with `//go:build !cgo` imports and calls
  `wasilibs/go-pgquery.Parse`.

No SQLGuard-specific build tag will be introduced. The standard `cgo` build
constraint already follows `CGO_ENABLED` and the target toolchain, so an
ordinary consumer build gets the required selection without learning a new
configuration surface. We will not enable `go-pgquery`'s optional
`pgquery_cgo` tag; its own documentation recommends the official library when
CGO is desired.

Using `go-pgquery` for every build was considered and rejected. It would move
existing consumers to the slower WASM path by default, while selecting its CGO
path requires a nonstandard tag and provides no benefit over the current
official dependency. Runtime selection and an injectable parser interface were
also rejected because they create configuration states that the conformance
contract does not need and would make a constructed engine's behavior less
obvious.

### 3. Keep parsing, error sanitization, and conversion shared

The shared `Parse` function will call `parseBackend`, immediately discard the
raw backend error, map every backend failure to the existing bounded internal
syntax category, and convert the returned protobuf tree with the current
reflection-based converter. Neither raw error nor raw tree will cross the
`internal/parser` boundary or be retained after conversion.

Because `go-pgquery.Parse` returns `*pg_query.ParseResult`, the shared code can
continue using the exact `pg_query_go/v6` descriptors. Importing the generated
protobuf package in a no-CGO build is supported by `go-pgquery` itself and does
not invoke the excluded native entry point.

Illustrative shape (names may be adjusted during implementation):

```go
// backend_cgo.go
//go:build cgo

package parser

import pgquery "github.com/pganalyze/pg_query_go/v6"

func parseBackend(sql string) (*pgquery.ParseResult, error) {
	return pgquery.Parse(sql)
}
```

```go
// backend_nocgo.go
//go:build !cgo

package parser

import (
	pgquery "github.com/pganalyze/pg_query_go/v6"
	wasmquery "github.com/wasilibs/go-pgquery"
)

func parseBackend(sql string) (*pgquery.ParseResult, error) {
	return wasmquery.Parse(sql)
}
```

```go
// pgquery.go (shared)
func Parse(sql string) (*Result, error) {
	tree, err := parseBackend(sql)
	if err != nil {
		return nil, &Error{category: FailureSyntax}
	}

	return convertResult(tree), nil
}
```

The parser call remains synchronous. SQLGuard will not move WASM compilation
or parsing to an unbounded goroutine. Existing context checks before and after
parsing therefore keep their ordering and cancellation precedence.

### 4. Use one checked-in conformance corpus for both build modes

`internal/parser/testdata/conformance` will contain intentionally non-secret
SQL cases and expected canonical parser-neutral results. Coverage will include:

- PostgreSQL 17-specific DML and DDL used by the project;
- comments, quoted identifiers, strings, dollar quoting, parameters, arrays,
  casts, operators, and representative literals;
- empty input and multiple top-level statements;
- data-modifying CTEs and recursively nested statement-bearing CTEs;
- representative malformed standalone input and a malformed member inside an
  otherwise valid batch;
- every statement kind and field accessed by built-in rules and shared
  traversal;
- canonical field/value/list snapshots used by representative custom rules.

The canonical representation will include every rule-visible node kind, field,
value kind, semantic value, and list order. Each ordinary parser test binary
will run the same table-driven suite against the backend selected for that
build. Checked-in expectations are reviewed from the current CGO baseline;
both `CGO_ENABLED=1` and `CGO_ENABLED=0` must match them. This avoids a false
comparison in which two backends share the same bug inside one test process.

The existing engine, rule, prepared-validation, privacy, and observability
suites will run unchanged in both build modes instead of duplicating those
assertions in backend-named tests. Backend-specific additions stay narrow: one
PostgreSQL 17 end-to-end engine case, raw WASM error sanitization, concurrent
first initialization, and deterministic malformed-input protection. Fuzzing
and race tests will run in both build modes. Backend errors and WASM faults
must never be included in returned errors, logs, metrics, or snapshots.

### 5. Treat performance and footprint as documented tradeoffs

The existing validation benchmarks remain the product-level measurement. CI or
documented maintainer commands will run the same benchmark set separately with
`CGO_ENABLED=1` and `CGO_ENABLED=0`; benchmark names and inputs remain
identical so `benchstat` can compare results. Add parser-focused fresh-process
first-parse and warm steady-state cases because WASM initialization can
otherwise be hidden by an already warmed process. The fresh-process benchmark
explicitly includes process and Go test startup rather than claiming to isolate
the parser initialization alone. Parallel benchmarks and `make test-race`
cover shared runtime behavior under load.

A small representative size-probe command under test tooling will import and
exercise SQLGuard so the linker retains the parser. It will be built twice with
the same Go version, target, flags, and stripped/unstripped setting. The report
will record executable bytes and, where the platform tooling is available,
section/symbol attribution. Module download size is recorded separately from
the linked binary because the no-CGO dependency still includes
`pg_query_go/v6` protobuf types and an embedded WASM artifact.

The measured table, commands, Go version, GOOS/GOARCH, compiler, dependency
revisions, and date will live in `docs/parser-backends.md`; README will summarize
the choice and link to it. No fabricated target ratio or size ceiling is used as
an acceptance criterion. Correctness gates selection, while measured cost tells
consumers when retaining CGO is preferable.

### 6. Make both modes first-class repository gates

The Makefile will retain `CGO_ENABLED ?= 1` and add explicit aggregate targets
for the supported matrix. At minimum, CI will run lint and the existing CGO
precommit path plus no-CGO unit tests, race tests, and compile checks on the
project's supported runner platforms. A no-CGO job must not install a C
compiler and will verify the selected package graph does not compile native
parser files.

Backend dependencies remain confined to `internal/parser`; the repository's
dependency guard will permit both parser imports only there. README consumer
requirements will explain that CGO remains the faster default when enabled and
that `CGO_ENABLED=0` selects the WASM backend automatically.

## Risks / Trade-offs

- **[WASM parsing is materially slower]** → Keep CGO as the default, publish
  SQLGuard-specific cold/warm and parallel measurements, and make the tradeoff
  explicit for high-volume callers. Upstream currently reports approximately
  4–5x slower parsing, but release documentation will use locally reproduced
  numbers.
- **[Embedded WASM and wazero increase binary size, startup latency, and
  memory]** → Measure a representative linked binary and first parse separately;
  document exact results and supported targets before release.
- **[The selected adapter has no tagged releases and a comparatively small
  maintainer base]** → Pin an immutable pseudo-version, review its source and
  notices, keep it behind a narrow internal entry point, and require conformance
  before every update.
- **[WASM-only defects can diverge from native `libpg_query`]** → Run the shared
  grammar/AST corpus, fuzz tests, race tests, and malformed-input tests in both
  modes; fail the release rather than add syntax-specific fallback logic.
- **[Protobuf or PostgreSQL grammar versions can drift between dependencies]**
  → Pin matching `pg_query_go/v6` and `go-pgquery` revisions and treat any
  descriptor or golden-snapshot change as an explicit reviewed compatibility
  update.
- **[WASM runtime support varies by GOOS/GOARCH and excludes TinyGo]** → Publish
  an explicit tested platform matrix; do not claim unsupported targets.
- **[Raw WASM/libpg_query diagnostics may contain submitted SQL]** → Discard
  backend errors at the parser boundary exactly as today and test errors,
  observability events, and panic/trap handling with sentinel secrets.
- **[Two build modes can accumulate accidental code drift]** → Limit each
  backend-specific file to the raw parse call and keep conversion, traversal,
  engine behavior, and tests shared.
- **[Changing roadmap order could be mistaken for deprioritizing or weakening
  audit mode]** → Change only the ordering constraint, keep audit mode as a
  separately required capability, and preserve its existing safety and privacy
  requirements.

## Migration Plan

1. Update product requirements to allow audit mode and no-CGO support to be
   delivered independently without changing either capability's guarantees.
2. Add the pinned no-CGO dependency and split only the raw parser entry point
   behind standard `cgo`/`!cgo` constraints; keep the current CGO file available
   throughout the migration.
3. Land the shared canonical corpus and require both builds to match before the
   no-CGO mode is described as supported.
4. Add the two-mode test/race/CI gates, dependency-boundary checks, benchmarks,
   and binary-size probe.
5. Record reviewed measurements, licenses, supported platforms, and operational
   limitations in `docs/parser-backends.md`, then update README consumer setup.
6. Release no-CGO support only after its behavior and documentation gates pass.

Rollback is compile-time and does not require caller migration: remove the
`!cgo` backend and its dependency, restore the documented CGO requirement, and
retain the unchanged CGO implementation. No persisted data or public API needs
conversion.
