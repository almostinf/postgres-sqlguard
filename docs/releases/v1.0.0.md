# postgres-sqlguard v1.0.0

`v1.0.0` is the first stable release of postgres-sqlguard: a
driver-independent Go library that rejects unsafe PostgreSQL statements before
an application sends them to a database.

## Highlights

- Parses the complete input with a PostgreSQL 17 grammar instead of relying on
  regular expressions or keyword matching.
- Fails closed on malformed SQL and inspects every top-level statement plus
  statement-bearing nested CTEs.
- Applies only explicitly registered built-in or application rules, in a
  deterministic order.
- Returns typed, privacy-safe errors without retaining SQL text, arguments,
  literal values, comments, credentials, or raw parser diagnostics.
- Provides opt-in Prometheus and `log/slog` integrations whose failures cannot
  replace or weaken a validation result.
- Supports the same public API and validation semantics with CGO enabled or
  disabled.

## Stable import paths

The stable public API is split across these packages:

| Purpose | Import path |
| --- | --- |
| Engine, rules contract, statements, prepared values, and typed errors | `github.com/almostinf/postgres-sqlguard` |
| Built-in rules | `github.com/almostinf/postgres-sqlguard/pkg/rules` |
| Prometheus metrics | `github.com/almostinf/postgres-sqlguard/pkg/observability/prometheus` |
| Structured logging | `github.com/almostinf/postgres-sqlguard/pkg/observability/slog` |

The example packages under `example/` demonstrate integration patterns; they
are not stable production adapters.

## Migration from pre-v1 versions

This release intentionally removes the former extension-package paths. Update
imports as follows:

| Before `v1.0.0` | `v1.0.0` |
| --- | --- |
| `github.com/almostinf/postgres-sqlguard/rules` | `github.com/almostinf/postgres-sqlguard/pkg/rules` |
| `github.com/almostinf/postgres-sqlguard/observability/prometheus` | `github.com/almostinf/postgres-sqlguard/pkg/observability/prometheus` |
| `github.com/almostinf/postgres-sqlguard/observability/slog` | `github.com/almostinf/postgres-sqlguard/pkg/observability/slog` |

No compatibility wrappers remain at the old paths. Constructor names, built-in
rule identifiers, rule ordering, observability dimensions, and validation
behavior are unchanged by the move.

## Requirements and parser backends

SQLGuard requires Go 1.26 and implements the grammar of the pinned PostgreSQL
17 parser. Compatibility with every older or newer PostgreSQL major version is
not implied.

| Build mode | Parser | Operational trade-off |
| --- | --- | --- |
| `CGO_ENABLED=1` | Native `libpg_query` through `pg_query_go` | Lowest measured validation cost and smaller binaries; requires a working C compiler and inherits CGO cross-compilation constraints. |
| `CGO_ENABLED=0` | Embedded `libpg_query` WebAssembly through `go-pgquery` and wazero | Requires no C compiler or custom build tag and simplifies cross-compilation; has higher measured cold-start time, memory use, validation latency, and binary size. |

Linux/amd64 is exercised in CI for both modes. Darwin/arm64 is supported and
was used for the release measurements. Other targets are not claimed until
they are added to the tested matrix, and TinyGo is not supported. See
[Parser backends](../parser-backends.md) for the complete support matrix and
the dated, reproducible measurements.

## Enforce-mode guarantees

Validation parses the entire input before evaluating policy. For valid SQL,
top-level statements are visited in input order, statement-bearing CTEs are
visited depth-first in declaration order, and rules run in registration order.
The first rejection returns a typed `Violation`; parser failures return a typed
`ParseError`.

Constructed engines and successful prepared values are safe for concurrent
use. Every prepared validation reevaluates the receiving engine's current rule
set. Caller cancellation and context values are preserved, although synchronous
parsing cannot be interrupted until the selected backend returns.

## Explicit non-goals

SQLGuard does not:

- execute SQL, bind arguments, open database connections, or intercept driver
  traffic;
- enforce PostgreSQL privileges or replace transactions, constraints,
  application authorization, or review;
- prove that arbitrary SQL is safe for a specific business operation or
  prevent every form of SQL injection;
- perform semantic tautology analysis such as rejecting `WHERE TRUE`;
- provide audit mode or an official database-driver adapter in `v1.0.0`;
- promise compatibility outside the documented Go, PostgreSQL grammar, and
  target matrix.

Applications remain responsible for routing every protected database call
through a validated boundary. Start with the [README](../../README.md), then
use the [validation guide](../validation-guide.md) and
[pgx integration guide](../pgx-integration.md) for details.
